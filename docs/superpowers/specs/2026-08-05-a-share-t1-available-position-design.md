# A 股 T+1 可用持仓设计规格

## 1. 目标

在现有证券实际持仓、实时回测监控和信号收件箱中引入 A 股 T+1 卖出约束。系统必须区分全部持仓与当日可卖持仓，防止当天买入或补仓的股份被错误卖出，同时保持现有账本、持仓组和历史消息兼容。

## 2. 范围与约束

- 仅处理 A 股股票持仓的 T+1 可卖数量。
- 不修改 `StockAnalysisPage.tsx` 及其概览、行情和 K 线路径。
- 继续使用 `sec_stock_position_ledger_v1` 作为唯一实际持仓账本，不升级或更换存储键。
- 继续使用交易流水动态推导可用持仓，不在持仓对象中永久保存容易失真的 `availableShares`。
- 旧持仓缺少完整交易流水时默认全部可用。
- 所有日期和交易日判断使用 `Asia/Shanghai`。
- 周末和法定休市日不计入下一交易日。

## 3. 术语

- `totalShares`：当前实际持仓总股数，即现有 `StockPosition.shares`。
- `availableShares`：截至指定时间允许卖出的股数。
- `frozenShares`：`totalShares - availableShares`，主要由尚未满足 T+1 的买入产生。
- `availableOn`：某笔买入股份最早允许卖出的交易日期。

## 4. 推荐架构

### 4.1 A 股交易日历

新增独立交易日历模块，提供：

```ts
isAStockTradingDay(date: string): boolean;
nextAStockTradingDay(date: string): string;
shanghaiTradingDate(value: Date | string): string;
```

交易日历必须同时处理周末和沪深交易所公告的法定休市日。日历数据应独立于 React 组件，使用可测试的本地数据源，并明确覆盖年份。

若计算涉及的年份不在日历覆盖范围内，系统不得仅按周一至周五猜测可用日期。可用持仓计算返回交易日历缺失错误，卖出入口进入不可执行状态，避免错误放行卖出。

### 4.2 可用持仓计算器

新增纯函数模块，从账本和交易流水动态计算：

```ts
interface StockPositionAvailability {
  totalShares: number;
  availableShares: number;
  frozenShares: number;
  nextAvailableDate: string | null;
}

calculateStockPositionAvailability(
  ledger: StockPositionLedger,
  code: string,
  asOf: Date | string,
): StockPositionAvailability;
```

计算规则：

1. 当前总持仓继续以 `StockPosition.shares` 为准。
2. 每笔买入流水的股份在其 `availableOn = nextAStockTradingDay(buyTradingDate)` 之前视为冻结。
3. `availableShares = min(totalShares, max(0, totalShares - 尚未解锁的买入股数))`。
4. 卖出只能从可用持仓中执行，因此同日卖出后，总持仓和可用持仓同时减少。
5. 若持仓没有可对应的完整买入流水，无法解释的存量部分视为历史基线持仓并默认可用。
6. 同日补仓仅冻结新增部分，不影响原有可用持仓。
7. 周五买入的股份最早在下周一或节后首个交易日可卖。

示例：

- 原有 300 股全部可用，当日补仓 200 股：总持仓 500，可用持仓 300。
- 当日卖出原有 100 股后：总持仓 400，可用持仓 200，冻结仍为 200。
- 下一交易日：总持仓 400，可用持仓 400。

## 5. 账本卖出校验

`sellStockPosition` 在写入前必须重新加载最新账本，并以交易时间重新计算可用持仓。

- 卖出数量不得超过 `availableShares`。
- 超限时抛出“卖出数量不能超过可用持仓”。
- 当 `availableShares` 为 0 时拒绝卖出。
- 保留现有 100 股整手校验和持仓总量校验。
- 为可重复测试，账本选项允许注入当前时间或直接使用 `input.tradedAt` 作为校验时点。
- 账本持久化成功前，不得更新收件箱消息执行状态。

## 6. 实际持仓界面

实际持仓表格不增加额外宽列。原“股数”列改为“全部 / 可用”。

每个单元格仅上下显示两个数字：

```text
500
300
```

- 上方数字为全部持仓。
- 下方数字为可用持仓，并使用稍浅的文字颜色区分。
- 单元格内不重复显示“全部”“可用”“冻结”等中文。
- 即使全部持仓均可用，也显示上下两个相同数字。
- 可用持仓为 0 时，卖出按钮禁用。
- 手动卖出弹窗的默认数量和最大允许数量均以可用持仓为准。
- 买入和补仓完成后，界面立即显示总持仓增加，而可用持仓保持不变。

## 7. 实时监控与信号收件箱

实时风险和策略判断继续基于全部持仓，但可执行卖出数量必须基于可用持仓。

监控持仓输入扩展为：

```ts
interface MonitorPosition {
  code: string;
  shares: number;
  availableShares: number;
  averageCost: number;
  openedAt: string;
}
```

信号规则：

- 技术性部分卖出使用可用持仓的 25%，继续按 100 股向下取整并保持最低 100 股。
- 止损和最长持仓期退出建议卖出全部可用持仓，而不是全部持仓。
- 可用持仓为 0 时不创建不可执行的卖出消息；买入方向的边沿状态仍正常更新。
- 卖出优先于补仓的现有规则保持不变。
- 收件箱打开交易弹窗时再次读取账本并重新计算可用数量。
- 若触发后可用数量下降，建议卖出数量降低到当前最大可卖整手并显示调整提示。
- 卖出后仍有总持仓时，消息标记为已卖出但 `positionRemaining` 保持 `true`。

消息模型增加兼容字段：

```ts
availableSharesAtSignal: number;
```

旧消息缺少该字段时按 `positionSharesAtSignal` 兼容读取，但执行前必须使用当前账本重新校验。

## 8. 错误处理

- 交易日历缺少年份：卖出入口禁用，并显示交易日历数据缺失。
- 持仓账本损坏：沿用现有账本错误处理，不推测可用数量。
- 卖出数量超过可用持仓：保持弹窗打开并显示校验错误。
- 收件箱历史建议数量超过当前可用持仓：自动下调到当前最大可卖整手。
- 当前可用持仓不足 100 股：不允许通过本系统生成整手卖出交易。

## 9. 测试要求

### 9.1 交易日历

- 普通工作日与周末判断。
- 周五买入、下周一解锁。
- 节前买入、节后首个交易日解锁。
- 上海时区跨日边界。
- 日历覆盖范围外安全失败。

### 9.2 可用持仓计算

- 当日首次买入全部冻结。
- 下一交易日全部解锁。
- 原持仓加当日补仓仅冻结新增部分。
- 同日卖出仅减少可用部分。
- 多笔买入在不同交易日分批解锁。
- 无完整流水的历史持仓全部可用。

### 9.3 账本与界面

- 卖出超过可用持仓被拒绝。
- 合法部分卖出成功。
- “全部 / 可用”列上下只显示两个数字。
- 可用为 0 时卖出按钮禁用。
- 买入后总持仓增加而可用持仓不增加。

### 9.4 实时信号

- 技术卖出建议不超过可用持仓。
- 全部卖出只建议全部可用持仓。
- 可用为 0 时不创建卖出消息。
- 历史建议数量在执行时按当前可用数量下调。
- 账本保存失败时不标记消息已执行。

### 9.5 回归保护

- 实际持仓、持仓组、自选股、收件箱和全局监控测试通过。
- `StockAnalysisPage.tsx` 及个股概览、实时价格和 K 线测试通过。
- TypeScript、Lint、生产构建和 `git diff --check` 通过。

## 10. 非目标

- 不实现港股、美股或基金的 T+0/T+1 规则。
- 不建立税务或成本核算用的逐笔持仓批次。
- 不改变现有平均成本计算方法。
- 不自动执行交易。
- 不修改个股分析页面。
