# 证券统一状态源渐进改造设计规格

## 背景与目标

证券系统目前由实际持仓、自选股、回测监控、信号收件箱、做 T 和策略复盘等模块分别读取 Supabase 或本地状态。同一账号的同一数据可能被多次请求，并因响应顺序不同出现短暂空白、旧数据覆盖新数据、监控股票集合不一致等问题。

本次改造建立应用内唯一的证券业务状态中心，在不增加 Supabase 表、不复制云端业务数据、不修改个股分析页和行情源的前提下，统一实际持仓与自选股的读取、写入后刷新和订阅。Supabase 继续作为云模式下的唯一权威数据源。

## 范围

本轮包含：

- 当前账号实际持仓账本的统一内存状态、加载、刷新和错误状态。
- 当前账号自选股结构的统一内存状态、加载、刷新和错误状态。
- 同类并发云请求合并。
- 请求版本控制，禁止旧响应覆盖新状态。
- 买入、卖出、持仓分组和自选变更后的统一失效与刷新。
- 回测监控、信号收件箱和做 T 对统一持仓、自选数据的订阅。
- 现有 hooks 的兼容外壳，支持逐步迁移。
- 关键流程和故障场景的自动化测试。

本轮不包含：

- 新建或修改 Supabase 业务表。
- 把行情、K 线、建议、报告、做 T 结果或虚拟仓历史写入新缓存。
- 修改个股分析页、`stock-api.ts` 或现有行情来源。
- 引入 Redux、Zustand、React Query 等新状态依赖。
- 一次性重写所有证券页面。

## 总体架构

新增应用级 `SecuritiesStateProvider`，挂载在认证上下文之内、证券页面和常驻监控之上。Provider 按当前登录账号维护以下状态：

- `positionLedger`：实际持仓账本。
- `watchlists`：当前账号自选股结构。
- 每类数据的 `loading`、`refreshing`、`error`、`updatedAt` 和递增请求版本。
- 当前正在执行的请求 Promise，用于合并并发读取。

Provider 不保存行情、K 线、短中线建议、信号历史、虚拟仓或做 T 结果。账号变化时立即隔离并重建状态，不复用上一账号的内存数据。

现有 `useStockPositionLedger`、`SecuritiesDataSourceProvider` 等入口保留为兼容层：若位于统一 Provider 内，直接订阅统一状态；若测试或独立组件未挂载 Provider，则安全降级到现有实现。迁移完成前不得因缺失 Provider 抛出整页错误。

## 数据读取与缓存

云模式初次加载顺序：

1. 读取当前账号受限本地缓存并立即显示。
2. 发起一次 Supabase 权威读取。
3. 多个消费者同时请求同类数据时复用同一个进行中的 Promise。
4. 云端成功后更新统一内存状态并覆盖当前账号本地缓存。
5. 云端失败时保留最近可用状态，只更新错误状态，不清空页面。

未登录模式继续使用现有本地账本和自选存储。现有缓存约束保持不变：仅缓存自选结构和实际持仓账本，当前账号隔离，24 小时过期，总量最高 500 KB，超限最旧优先清理，退出登录清理当前账号缓存。

## 并发与旧响应保护

每类资源维护独立递增请求版本。刷新开始时记录版本，响应返回时只有版本仍为当前最新版本才允许写入状态。买入、卖出、分组或自选变更会递增相关版本，使变更前发出的读取结果自动失效。

同一账号、同一资源、同一刷新代次的并发读取合并；显式强制刷新可以启动新版本，但不得让旧请求覆盖新请求结果。

## 写操作与跨模块同步

所有持仓写操作统一经状态中心执行：

- 写入 Supabase 成功后，立即触发一次权威持仓刷新。
- 刷新完成后，实际持仓面板、收件箱、回测监控、做 T 和复盘订阅者同时得到同一账本。
- 写入失败时保留原状态并展示错误，不进行乐观伪造。

自选股保存成功后执行同样的统一刷新逻辑。监控股票集合统一由“当前账号自选代码 + 当前账号实际持仓代码”计算，不再使用默认自选覆盖账号数据。

## 分阶段迁移

### 第一阶段：实际持仓

建立 Provider 的基础框架、请求合并和版本保护；迁移 `useStockPositionLedger`、`SecuritiesDataSourceProvider` 和实际持仓面板。验证买入、卖出、分组和页面切换。

### 第二阶段：自选股

把 `WatchlistPage` 的云读取和保存迁入状态中心，保留现有界面与建议计算逻辑。

### 第三阶段：监控与交易联动

让 `RealtimeBacktestMonitorProvider`、信号收件箱、做 T 和策略复盘订阅统一的账号自选与持仓集合，删除重复读取路径。

每一阶段必须独立通过测试、类型检查、lint 和生产构建后才能进入下一阶段。任何阶段出现回归时，停止后续迁移并修复当前阶段。

## 错误隔离与恢复

- Provider 只暴露资源级错误，不抛出导致整个路由崩溃的异常。
- 持仓失败不能清空自选，自选失败不能停止监控已有持仓。
- 页面显示最近可用数据和同步失败提示，并提供统一重试入口。
- 组件卸载或账号切换后，已返回的旧请求不得更新新账号状态。
- 兼容层在无 Provider 的单元测试和独立渲染场景下继续安全降级。

## 验收标准

- 多个持仓消费者同时挂载时，Supabase 持仓读取只发生一次。
- 慢请求先发、快请求后发时，慢请求结果不能覆盖快请求结果。
- 云端失败时缓存持仓或自选继续显示。
- 买入、卖出或分组后，所有订阅模块看到同一账本版本。
- 当前账号的监控集合准确等于其自选与实际持仓代码的并集。
- 切换账号后不显示前一账号的内存状态或缓存。
- 未挂载统一 Provider 的现有测试组件不会崩溃。
- 不新增 Supabase 表，不增加云端业务数据副本。
- 个股分析页和行情源相关回归测试保持通过。

## 验证策略

采用 TDD，优先覆盖请求合并、旧响应保护、账号切换、失败保留、写后统一刷新和监控集合计算。阶段完成后运行证券相关集成测试、TypeScript 类型检查、lint、生产构建及 `git diff --check`。本地 5173 页面需可正常打开，关键页面不得出现 ErrorBoundary 或黑屏。
