# 云端常驻证券信号监控设计规格

日期：2026-08-07  
状态：待最终复核  
范围：证券项目中的自选股、实际持仓、虚拟仓、信号收件箱与浏览器推送

## 1. 背景

当前实时信号监控完全运行在浏览器中。自选股、实际持仓、虚拟交易记录和收件箱主要保存在 `localStorage`，行情刷新依赖页面处于打开且可见状态。网页关闭、电脑休眠或浏览器暂停后台页面后，扫描随即停止，因此不能持续捕获买入、补仓和卖出时机。

本次升级将监控职责迁移到云端常驻进程。用户关闭网页后，系统仍应在A股交易时段持续扫描；触发信号时将结果写入云端收件箱并发送浏览器推送。现有网页继续承担账户管理、数据维护、信号展示和交易确认，不直接连接券商自动下单。

## 2. 已确认决策

- 运行方式：云端常驻监控，不依赖用户电脑持续开机。
- 账户方式：邮箱和密码登录。
- 云平台：Supabase负责身份认证和数据库，Railway负责常驻Worker。
- 通知方式：网站收件箱与浏览器Web Push同时支持。
- 扫描频率：A股交易时段目标约3秒；休市、午休、周末和法定非交易日暂停。
- 监控范围：全部自选股、全部实际持仓和全部未平仓虚拟持仓。
- 执行边界：只生成分析信号和模拟交易，不自动连接券商下单。
- 原有约束：100股默认买入/补仓、允许部分卖出做T、A股T+1和可用股数约束继续生效。

## 3. 目标与非目标

### 3.1 目标

1. 网页关闭后仍持续扫描用户的监控范围。
2. 在信号触发时保存实时价格、建议数量、依据、策略版本和时间。
3. 防止3秒轮询产生重复消息，同时允许同一信号消失后再次出现时建立新周期。
4. 将用户已有浏览器数据安全、幂等地迁移到云端。
5. 支持同一账户在多台电脑使用，并同步自选股、持仓、收件箱和执行记录。
6. 为未来多用户商业化提供数据隔离、审计、容量控制和健康监控基础。

### 3.2 非目标

- 本阶段不连接券商交易接口，不自动下单。
- 本阶段不提供短信、电话、微信或邮件即时交易提醒；邮箱仅用于账户身份。
- 本阶段不重新设计个股分析页面或改变其回测展示。
- 本阶段不更换现有技术指标与信号规则，只将经验证的规则迁移为前后端共享核心。
- 本阶段不训练新的机器学习模型。

## 4. 总体架构

系统分为四层：

1. **网页客户端**：注册登录、数据迁移、自选股和持仓维护、收件箱订阅、推送授权、信号执行确认及系统状态展示。
2. **Supabase Auth与PostgreSQL**：用户认证、按用户隔离的监控数据、信号、虚拟仓、审计记录和推送订阅。
3. **Railway常驻Worker**：交易日历判断、行情聚合、K线缓存、策略计算、信号状态机、虚拟交易和通知投递。
4. **Web Push服务**：Worker使用VAPID密钥向用户已授权的浏览器设备发送推送；投递失败不能回滚已经写入的收件箱消息。

网页现有前端监控保留为显式备用通道。云端健康时，前端只订阅云端信号，不再独立生成正式消息；云端异常时，用户可手动启用本地临时扫描。本地临时信号必须标记来源，且不得与云端信号使用相同的正式唯一键。

## 5. 组件边界

### 5.1 共享策略核心

从现有浏览器监控中提取无浏览器依赖的纯TypeScript核心，至少包括：

- 实时行情合并日K线。
- 技术指标计算与策略判断。
- 买入、补仓、部分卖出、全部卖出决策。
- 虚拟仓交易状态机。
- T+1可用数量和下一可卖交易日计算。
- 信号周期和去重键计算。

共享核心不得读取 `localStorage`、DOM或React状态。网页回退监控与Railway Worker必须调用同一套核心，避免两个回测引擎继续分叉。

### 5.2 网页客户端

客户端负责：

- 邮箱密码注册、登录、退出和密码重置。
- 首次登录数据迁移。
- 云端自选股、持仓组、持仓交易和策略配置的增删改查。
- 通过Supabase Realtime订阅新信号和状态变化。
- 注册、更新和撤销Web Push订阅。
- 展示云端Worker健康状态及最后扫描摘要。
- 用户点击信号后的实际交易确认。

### 5.3 常驻Worker

Worker负责：

- 获取需要监控的全部活跃股票代码并全局去重。
- 按行情接口批量上限分组请求，并共享同一代码的行情结果。
- 缓存历史K线和指标基础数据，避免每3秒重新下载历史数据。
- 根据每位用户的自选股、实际持仓、虚拟仓和策略版本计算决策。
- 原子写入信号、股票信号状态、虚拟交易和审计事件。
- 投递Web Push并记录结果。
- 写入Worker心跳、扫描统计和错误摘要。

## 6. 数据模型

所有业务表均包含 `user_id`，并启用Supabase Row Level Security。

### 6.1 账户和设备

- `profiles`：用户偏好、时区、迁移状态和账户状态。
- `push_subscriptions`：浏览器推送端点、公钥、设备标签、最后成功时间、失效时间。

### 6.2 用户投资数据

- `watchlists`：自选股分组。
- `watchlist_items`：自选股票代码、加入时间和监控开关。
- `position_groups`：实际持仓组。
- `positions`：代码、总股数、平均成本、所属组和当前状态。
- `position_lots`：每次买入批次、交易日、剩余数量，用于T+1可用数量计算。
- `position_transactions`：买入、补仓、部分卖出、全部卖出的不可变流水。
- `strategy_assignments`：用户当前启用的策略ID、版本和参数快照。

### 6.3 信号和虚拟交易

- `signal_states`：每位用户每只股票当前买卖方向、活跃周期和待执行T+1任务。
- `signal_alerts`：网站收件箱消息及触发快照。
- `virtual_positions`、`virtual_lots`、`virtual_transactions`、`virtual_cycles`：云端虚拟仓及完整回测记录。
- `notification_deliveries`：每条信号向每台设备的投递结果。
- `audit_events`：迁移、策略变化、信号生成、用户执行和管理员操作。

### 6.4 运行状态

- `worker_leases`：Worker主实例租约，防止多实例重复扫描。
- `worker_heartbeats`：最后心跳、版本、运行状态和处理延迟。
- `scan_runs`：扫描开始/结束时间、代码数量、用户数量、成功数、失败数和行情时间。
- `market_data_failures`：按数据源和代码记录可诊断错误。

## 7. 信号数据流

1. Worker确认当前是否为A股交易时段。
2. Worker取得所有启用监控用户的自选股、实际持仓和未平仓虚拟持仓。
3. 股票代码全局去重后批量请求实时行情。
4. Worker只为缺失或过期代码加载历史K线，随后合并当前实时行情。
5. 共享策略核心分别计算：
   - 自选股首次买入判断；
   - 实际持仓补仓和卖出判断；
   - 虚拟持仓补仓和卖出判断。
6. 信号状态机判断这是新周期、持续状态、状态解除还是反向信号。
7. 新周期通过数据库唯一约束原子写入，持续状态不重复通知。
8. 虚拟仓在同一事务中记录模拟成交；实际持仓只产生建议，不自动改变。
9. 收件箱写入成功后异步发送Web Push。
10. 已打开网页通过实时订阅立即显示新消息；重新打开网页时从数据库补齐未读消息。

## 8. 信号周期与去重

正式信号唯一性必须以状态周期为基础，不能永久按股票和方向去重。

建议唯一键组成：

`user_id + code + strategy_id + strategy_version + action + intent + cycle_id`

规则如下：

- `hold -> buy`：建立新的买入周期并通知。
- `buy -> buy`：持续状态，不重复通知。
- `buy -> hold`：关闭买入周期；以后再次变成buy可建立新周期。
- 卖出、补仓和T+1待卖遵循同样状态周期原则。
- Worker重启后从数据库中的 `signal_states` 恢复，不因内存清空重复生成消息。
- 数据库唯一约束是最终防重层，不能只依赖进程内存。

## 9. 实际持仓与T+1

- 买入和补仓默认建议100股，用户执行时可修改为合法的100股整数倍。
- 每笔实际买入写入独立lot，并记录上海交易日期。
- 总股数为所有未结清lot之和；可用股数只包含早于当前交易日买入的剩余lot。
- 普通技术卖出可建议部分卖出；止损、最长持有期等退出信号可建议全部可用股数。
- 当卖出信号出现但可用股数不足100股时，建立T+1待复核任务，而不是生成无法执行的正式卖出成交。
- 下一交易日按当时实时价格和最新信号重新验证；普通技术信号失效则取消，止损和超期等持续风险按既定规则继续处理。

## 10. 浏览器推送

- 用户首次开启推送时由浏览器明确请求权限。
- 每台设备生成独立订阅，可在设置页查看和撤销。
- 推送内容包含股票名称、代码、动作、建议数量、触发价格和简要依据；不包含账户密码或完整持仓资产。
- 点击推送打开对应收件箱消息或股票分析页面。
- 推送失败、权限被撤销或端点过期时，标记投递失败并清理无效订阅，但不得删除信号。
- 收件箱数据库记录是事实来源，推送只是提醒渠道。

## 11. 首次迁移和离线同步

### 11.1 首次迁移

首次登录后，客户端检测本地数据并展示迁移摘要。用户确认后上传：

- 自选股及分组；
- 实际持仓组、持仓、lot和交易记录；
- 当前策略配置；
- 历史信号和虚拟交易记录。

每次迁移使用稳定的 `migration_id` 和本地对象来源ID。服务端唯一约束保证重复提交不会复制数据。迁移完成前保留本地数据；完成并校验数量后标记云端为主数据源。

### 11.2 在线写入与离线处理

- 在线时，交易类操作以云端事务成功为完成条件。
- 普通自选股编辑可采用乐观界面更新，失败后回滚并提示。
- 离线修改进入本地待同步队列，恢复网络后按创建顺序提交。
- 持仓交易冲突不得静默覆盖；客户端需要重新读取最新持仓并要求用户确认。

## 12. 交易日历和扫描调度

- Worker使用Asia/Shanghai时区和A股交易日历。
- 正常扫描窗口与现有产品保持一致：上午、下午交易窗口内约3秒一次。
- 午休、收盘、周末及已配置法定休市日暂停实时扫描。
- 开盘前加载当日活跃监控范围和K线缓存；开盘后立即执行首轮扫描。
- 监控范围变化通过数据库变更订阅或短周期增量刷新进入Worker，无需重启。
- 每轮扫描若耗时超过目标间隔，不并发堆积下一轮；完成后立即开始下一轮，并记录延迟。

## 13. 并发、容量与成本控制

- 所有用户的相同股票在一轮中只请求一次行情。
- K线按 `code + trading_date` 缓存，盘中主要更新当日bar。
- 行情按提供商批量上限分批，并设置最大并发。
- 初始阶段使用一个主Worker和数据库租约；扩容时按代码分片，但同一用户股票状态仍通过数据库事务串行化。
- 用户订阅数量可按产品套餐设置上限，但本阶段不实现计费。
- 扫描指标至少包含独立代码数、用户标的关联数、行情请求数、缓存命中率和单轮耗时。

## 14. 错误处理和恢复

- 单个股票行情或K线失败只影响该股票，不阻塞整轮。
- 数据源失败采用指数退避、超时和熔断；恢复后自动重新加入扫描。
- 失败的股票不得使用过期价格生成新信号。
- 数据库暂时不可用时不得在内存中宣告正式信号；恢复后从最后成功状态重新扫描。
- Worker异常退出后由Railway自动重启，并通过租约和数据库状态恢复。
- Web Push失败只更新投递状态，可按策略重试，不回滚信号。
- 前端展示云端在线、延迟、降级和离线四种状态，不能用“实时监听中”掩盖后台故障。

## 15. 安全与权限

- 使用Supabase Auth邮箱密码账户；密码不进入业务表。
- 业务表启用RLS，普通客户端只能访问 `auth.uid() = user_id` 的记录。
- Railway Worker使用仅存在于服务端环境变量中的Service Role密钥。
- VAPID私钥、数据库服务密钥和行情服务凭据不得进入Vite客户端环境变量。
- 关键写入使用服务端校验和数据库约束，不能信任客户端提交的用户ID、可用股数或信号状态。
- 审计记录追加写入，普通用户不得修改历史审计事件。
- 提供账户数据导出、推送撤销和账户停用能力，为商业化合规预留接口。

## 16. 前端体验

收件箱顶部状态区增加：

- 云端Worker状态和最后心跳；
- 最后扫描时间、行情时间；
- 监控自选股数、实际持仓数、虚拟持仓数；
- 本轮成功、失败和新增信号数；
- 推送权限与当前设备状态。

没有新信号时显示“最近一轮已扫描N只，未触发新的买入/补仓/卖出条件”，避免用户误以为收件箱卡死。云端故障时明确显示原因和恢复状态，并提供一次手动本地扫描入口。

## 17. 测试策略

### 17.1 共享策略核心

- 前端与Worker对同一行情、K线和持仓输入产生完全一致的决策。
- 买入、补仓、部分卖出、全部卖出及无信号场景。
- T+1可用数量、下一交易日和复核取消。
- 信号周期解除后再次触发可生成新消息。

### 17.2 数据库和权限

- RLS阻止跨用户读取和写入。
- 信号唯一约束在并发写入时只保留一条。
- 持仓交易和虚拟成交事务失败时全部回滚。
- 首次迁移重复提交保持幂等。

### 17.3 Worker

- 全部自选股和持仓均进入监控，不存在固定4只或其他截断。
- 相同股票跨用户只请求一次行情。
- 单代码失败不阻塞其他代码。
- Worker重启不重复推送持续信号。
- 租约阻止两个实例同时成为主扫描器。
- 休市、午休和非交易日不执行实时扫描。
- 推送失败仍保留收件箱消息。

### 17.4 前端

- 注册、登录、退出和密码重置。
- 首次迁移摘要、成功校验和失败恢复。
- Supabase Realtime收到新信号后更新未读数。
- 推送授权、撤销和无权限降级。
- 云端状态、无新信号状态和故障状态清晰可见。
- 个股分析页面回归测试保持通过。

## 18. 分阶段交付

### 阶段A：云基础和账户

建立Supabase项目配置、数据库迁移、RLS、邮箱密码认证和前端会话管理。

### 阶段B：云端业务数据

迁移自选股、持仓组、实际持仓、交易流水和策略配置；实现首次本地数据迁移。

### 阶段C：共享策略核心与Worker

提取共享策略核心，建立Railway Worker、行情聚合、K线缓存、信号状态机、虚拟仓和健康状态。

### 阶段D：收件箱同步和Web Push

将网页收件箱切换为云端订阅，完成推送授权、投递和设备管理。

### 阶段E：降级、审计和商业化基础

完成本地手动扫描降级、审计轨迹、状态面板、容量指标、故障恢复和全链路回归。

每个阶段必须独立可验证；在云端Worker和迁移完成前，现有本地监控继续可用。

## 19. 验收标准

1. 关闭网站至少30分钟后，测试信号仍由Worker生成并保存；重新登录可看到完整消息。
2. 已授权设备在网页关闭时能收到浏览器推送。
3. 全部自选股、实际持仓和未平仓虚拟持仓均进入扫描，页面显示准确数量。
4. 同一持续信号不会每3秒重复；解除后再次触发会建立新周期。
5. 每条信号包含触发时实时价格、数量、依据、策略版本和时间。
6. 点击执行买入或卖出后，云端持仓和Worker下一轮输入同步更新。
7. T+1、总股数、可用股数和部分卖出规则与现有正式规格一致。
8. 一个用户无法访问另一个用户的任何证券业务数据。
9. Worker重启、行情局部失败和推送失败不会造成重复交易或丢失收件箱消息。
10. 个股分析页面及现有股票功能回归测试保持通过。

## 20. 上线前置条件

实施和部署需要用户提供或创建：

- Supabase项目及其URL、Anon Key、Service Role Key；
- Railway项目及部署权限；
