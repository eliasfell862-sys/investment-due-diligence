# 云端虚拟组合共享本金与全持仓做 T 设计规格

## 1. 目标

云端虚拟持仓改为一个账号共享一套资金账户，初始本金固定为 200,000 元。任何普通买入、补仓或做 T 回补都不得使组合可用现金小于零。所有仍在持有的云端虚拟股票均进入做 T 扫描，不设置单独白名单。

本功能只影响云端虚拟持仓、虚拟交易流水、虚拟做 T 信号和相关复盘数据，不修改实际持仓、实盘下单、东方财富 OCR 或本地影子交易验证功能。

## 2. 已确认规则

- 200,000 元是整个账号所有虚拟股票共享的本金，不是单只股票额度。
- 资金约束按真实现金流计算，而不是按实时市值计算。
- 买入占用资金包含成交金额和买入手续费。
- 卖出释放资金按扣除卖出手续费、印花税和其他适用费用后的净到账计算。
- 股票价格上涨不会提高本金，也不会因为市值超过 200,000 元而被强制卖出。
- 账户可以反复使用卖出释放的现金，但任何时刻不得透支。
- 历史记录按交易时间从早到晚重放。资金不足的买入及其关联交易组不再保留。
- 所有云端虚拟持仓都可参与做 T，但做 T 卖出仍受 A 股 T+1、100 股整手和可用股数限制。

## 3. 推荐架构

### 3.1 虚拟资金账户

新增 `virtual_cash_accounts`，每个用户只有一行：

- `user_id uuid primary key`
- `initial_capital numeric not null default 200000`
- `cash_balance numeric not null`
- `reserved_cash numeric not null default 0`
- `version bigint not null default 0`
- `updated_at timestamptz not null`

`cash_balance` 表示已经完成虚拟成交后的可用现金。`reserved_cash` 为后续异步下单预留；本阶段的信号成交在单个数据库事务内完成，正常情况下保持为零。保留该字段是为了防止未来把“信号”和“成交”拆开时破坏资金约束。

账户首次创建时 `initial_capital = cash_balance = 200000`。不得由前端传入其他本金覆盖这一规则。

### 3.2 交易现金快照

扩展 `virtual_transactions`，保存每次交易对应的现金变化：

- `gross_amount numeric`：成交价乘股数。
- `fee_amount numeric`：该次成交全部费用。
- `cash_delta numeric`：买入为负，卖出为正。
- `cash_balance_after numeric`：成交后的共享现金余额。
- `fee_profile_snapshot jsonb`：本次使用的费率快照。
- `fee_estimated boolean`：历史重放无法取得原始费率时标记为 `true`。

新交易必须保存费用快照，避免用户以后修改费率导致历史资金和收益被重算。

## 4. 原子交易与并发保护

现有 `commit_signal_transition` 仍是云端信号与虚拟成交的唯一写入口。执行虚拟交易时必须：

1. 在同一事务中按 `user_id` 锁定 `virtual_cash_accounts` 行。
2. 读取并锁定对应虚拟持仓和可用批次。
3. 使用统一费用引擎计算成交金额、费用及现金变化。
4. 买入前校验 `cash_balance >= gross_amount + fee_amount`。
5. 校验通过后同时更新资金账户、虚拟持仓、批次、交易、周期、信号和审计事件。
6. 任一步失败则整个事务回滚，禁止出现“收件箱显示已成交但持仓或现金没有变化”。

两个股票同时触发买入时，数据库行锁保证它们串行消费同一笔共享现金。前端余额检查只用于即时提示，数据库检查才是最终约束。

资金不足时不创建虚拟成交、不改变持仓；信号保留为被阻止状态，原因使用稳定代码 `virtual_cash_insufficient`，并展示需要资金、可用现金和缺口。金额只对当前登录用户可见。

## 5. 全持仓做 T

### 5.1 扫描范围

云端扫描集合为：

- 当前用户全部自选股；
- 当前用户全部实际持仓；
- 当前用户全部未平仓虚拟持仓；
- 当前用户全部未完成做 T 周期。

虚拟持仓不受自选股变化影响。即使股票从自选股删除，只要仍有虚拟仓位或未完成做 T 周期，就继续扫描。

### 5.2 做 T 状态

每只虚拟持仓独立维护做 T 周期：

1. 达到做 T 卖出条件时，只能卖出已满足 T+1 的可用股份。
2. 建议数量按现有动态做 T 数量引擎计算，向下取 100 股整手；不足 100 股不生成成交信号。
3. 卖出净到账立即进入共享现金账户。
4. 回补价格满足条件时，回补金额连同费用不得超过共享可用现金。
5. 共享现金被其他股票占用导致无法回补时，周期进入 `buyback_blocked_by_cash`，继续监测并明确提示风险，不得透支完成回补。
6. 做 T 收益按已配对股数确认，扣除完整双边费用；未回补部分不得提前计为完整做 T 收益。

“每只股票都可以做 T”表示所有虚拟持仓都进入同一套资格评估，并不表示系统会无条件或每天强制做 T。行情、K 线、流动性、费用后净收益、T+1 可用股数和风险条件仍必须通过。

## 6. 历史账本清理与重建

### 6.1 安全流程

历史清理分为只读预演和正式执行两步：

1. 读取当前用户全部 `virtual_transactions`、`virtual_cycles`、`virtual_positions`、`virtual_lots` 和关联虚拟信号。
2. 按 `traded_at`、交易 ID 稳定排序后从 200,000 元开始重放。
3. 卖出必须引用此前已保留的持仓和批次；孤立卖出不得单独保留。
4. 若某笔买入的成交金额加费用超过当时可用现金，则拒绝该笔买入，并删除它所属的整个关联交易组。
5. 关联交易组包括该买入创建或追加的批次、依赖该批次的后续卖出、对应周期、持仓派生结果、虚拟成交信号和相关复盘引用。
6. 重放结束后从保留交易重新生成持仓、批次、周期汇总和资金账户，不直接信任旧汇总字段。

### 6.2 费用缺失处理

旧交易没有费用快照时，预演使用用户当前有效的交易费率配置重算，并标记 `fee_estimated = true`。若用户没有有效费率配置，清理被阻断，不使用零费用静默通过。

### 6.3 预演报告

正式删除前必须向用户展示：

- 原交易数、保留交易数和删除交易数；
- 原持仓数、重建后持仓数；
- 被删除的交易组数量及股票代码；
- 重建后的已占用成本、可用现金和累计费用；
- 是否包含估算费用；
- 一次性预演 ID 和数据快照时间。

正式执行必须携带该预演 ID。若云端数据在预演后发生变化，执行失败并要求重新预演，防止误删新交易。

### 6.4 删除边界

正式清理只删除当前登录用户的超额虚拟交易组。不得影响：

- 其他用户的数据；
- 实际持仓及实际交易流水；
- 自选股；
- 普通信号历史中与被删虚拟成交无关的消息；
- 策略参数和费率配置。

删除和重建在一个数据库事务内完成，并写入审计事件。审计只保存预演摘要、删除对象 ID 和前后余额，不复制完整行情或敏感页面内容。

## 7. 页面展示

云端虚拟持仓区域增加组合资金摘要：

- 初始本金：200,000 元；
- 可用现金；
- 持仓成本；
- 当前市值；
- 浮动盈亏；
- 资金使用率；
- 未完成做 T 周期数。

买入或回补被资金约束阻止时，收件箱和虚拟仓页面显示同一原因。页面不得把当前市值误写为本金占用，也不得以实时市值变化直接修改可用现金。

## 8. 本地与云端一致性

共享本金约束首先在纯 TypeScript 虚拟账本中实现，供本地测试、回测和前端预览复用；云端 RPC 使用相同的计算口径并进行最终原子校验。

本地账本升级时加入资金账户字段或等价的派生接口。旧本地 V1 数据迁移为 200,000 元初始本金；若旧数据超额，仅在用户主动执行清理时删除，不在页面加载时静默修改历史。

## 9. 错误处理

- `virtual_cash_insufficient`：共享可用现金不足。
- `virtual_fee_profile_missing`：无法计算费用。
- `virtual_history_replay_conflict`：历史交易依赖关系不完整。
- `virtual_cleanup_snapshot_stale`：预演后数据已变化。
- `virtual_t_buyback_cash_blocked`：做 T 回补因共享现金不足被阻止。
- `virtual_position_not_available_t1`：做 T 卖出股份尚不可用。

所有错误必须保持交易原子性，失败后不得留下部分持仓、部分批次或负现金。

## 10. 测试要求

### 10.1 纯账本测试

- 多只股票共享 200,000 元，而不是各自拥有 200,000 元。
- 买入金额加费用刚好等于余额时允许成交，超过 0.01 元时拒绝。
- 卖出净到账可被另一只股票后续使用。
- 市值上涨或下跌不改变可用现金。
- 并发语义下不能产生负余额。
- 资金不足不会生成虚拟交易或修改持仓。

### 10.2 做 T 测试

- 每只未平仓虚拟股票都进入做 T 扫描。
- 从自选股删除后仍继续扫描虚拟持仓。
- T+1 不可用股份不能做 T 卖出。
- 做 T 卖出净到账增加共享现金。
- 回补金额与费用超过余额时阻止回补并保留周期。
- 多只股票同时触发回补时共享同一现金上限。
- 完整与部分回补均正确计算双边费用和净收益。

### 10.3 历史清理测试

- 按时间重放并保留资金可覆盖的交易组。
- 删除第一笔超额买入及其全部依赖记录，不留下孤立卖出。
- 早期卖出释放的现金可以支持后续买入。
- 旧交易费用被估算并在报告中标记。
- 数据在预演后变化时禁止执行。
- 清理只影响指定用户。
- 清理后持仓、批次、周期、交易、信号和资金余额完全一致。

### 10.4 数据库与集成测试

- `commit_signal_transition` 在两个并发买入请求下最多允许资金可覆盖的请求成交。
- RPC 失败时所有写入回滚。
- Railway 常驻扫描、登录后的前台扫描和本地账本对同一输入产生相同资金决定。
- 云端页面刷新后资金、持仓和做 T 周期不丢失。

## 11. 验收标准

1. 当前用户全部云端虚拟持仓合计只能使用共享的 200,000 元初始本金。
2. 任意买入、补仓或做 T 回补都不能造成负现金。
3. 所有虚拟持仓均被做 T 引擎扫描，且继续遵守 T+1、整手、费用后盈利和风险约束。
4. 历史超额记录经过预演确认后可被一致地清理，清理后不存在孤立记录。
5. 页面明确显示本金、可用现金、持仓成本和资金使用率。
6. 云端并发扫描不会突破资金上限。
7. 实际持仓、实盘功能、OCR 和其他用户数据不受影响。

## 12. 实施边界

本规格不包含自动实盘下单、融资融券、卖空做 T、追加本金、多个虚拟资金账户或按策略拆分本金。未来如需修改 200,000 元本金，必须作为独立、可审计的资金调整功能设计，不能直接编辑数据库余额。
