# 多用户证券工作台设计规格

## 1. 目标

把证券工作台从依赖浏览器本地存储的单用户应用，升级为基于邮箱账户的多用户系统。

用户注册并验证邮箱后登录，直接进入自己的证券工作台。不同账户的数据相互隔离；同一账户可在多台设备同时登录并实时同步。刷新页面、关闭浏览器或更换电脑后，个人数据仍可恢复。

本阶段不改造基金数据接口，不迁移投研项目和投研文档，也不修改股票个股分析算法。

## 2. 范围

第一阶段纳入以下证券个人数据：

- 自选股池、自选分组和分组成员
- 实际持仓、持仓组、T+1持仓批次和交易记录
- 虚拟持仓、虚拟交易和回测记录
- 策略配置、策略分配和策略学习结果
- 收件箱消息、已读状态和执行状态
- 提前布局雷达保存结果
- 用户偏好和必要的功能配置
- 数据导入、交易和策略变更审计轨迹

不纳入本阶段：

- 投研项目、尽调证据、文档和报告
- 基金行情接口修复
- 股票目录、实时行情、K线等公共市场数据
- 个股分析、估值和交易策略算法改造
- 云端持续扫描全部股票

## 3. 总体架构

采用 Supabase Auth + PostgreSQL分表存储 + Row Level Security + Supabase Realtime。

- Netlify部署静态前端。
- Supabase提供邮箱认证、数据库、Realtime和权限控制。
- Supabase是证券个人数据的正式数据源。
- localStorage和IndexedDB只作为当前登录账户的本地缓存和迁移来源，不能再决定数据归属。
- 股票目录、实时行情、K线和其他公开市场数据继续按需获取，不为每个用户重复存储。
- 前端只能使用 Supabase anon public key。
- service_role key、邮箱服务密码和数据库管理员密钥不得进入浏览器包。

## 4. 账户与导航

### 4.1 注册和登录

- 用户使用邮箱和密码自行注册。
- 注册必须完成邮箱验证。
- 支持登录、退出、忘记密码和密码重置。
- 登录会话持久化并自动刷新。
- 会话过期、被撤销或账户被禁用后，立即清空内存中的个人数据并跳转登录页。

### 4.2 路由

- 未登录用户不能访问证券工作台及证券子页面。
- 未登录访问受保护路径时跳转登录页，并保存原目标地址。
- 正常登录后默认进入 `/securities`。
- 密码重置回调继续使用独立登录路由。
- 退出登录后返回登录页，不显示上一位用户的工作台数据。

### 4.3 并发登录

- 支持不同账户同时在线。
- 支持同一账户在多台电脑和多个浏览器同时登录。
- 不采用“新设备登录踢出旧设备”的策略。

## 5. 数据所有权和隔离

每张个人数据表必须包含：

- `user_id uuid not null`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`
- 必要时包含 `version bigint not null`
- 必要时包含稳定的 `source_id text` 或幂等键

所有个人表启用 RLS：

- `select`：仅允许 `auth.uid() = user_id`
- `insert`：仅允许写入自己的 `user_id`
- `update`：仅允许修改自己的记录
- `delete`：仅允许删除自己的记录
- 所有安全定义者函数必须显式验证 `auth.uid()`

前端传入其他用户的 `user_id` 时，数据库必须拒绝，而不是依赖界面隐藏。

## 6. 数据模型

### 6.1 自选股

- `watchlists`：股池名称、排序和账户归属
- `watchlist_items`：股票代码、股池归属、启用状态和稳定来源 ID
- `watchlist_groups`：股池内标签或分组
- `watchlist_item_groups`：股票与标签的多对多关系

自选股增删采用单条增量操作，不覆盖整份股池 JSON。

### 6.2 实际持仓

- `position_groups`：持仓组
- `positions`：当前持仓汇总
- `position_lots`：买入批次、总股数、可用日期和剩余股数
- `position_transactions`：买入、补仓、减仓和卖出记录

买卖操作通过数据库 RPC/事务执行，保证持仓、批次、交易记录和消息状态同时成功或同时失败。

A股 T+1 可用数量以持仓批次计算，不仅保存一个可用股数字段。

### 6.3 虚拟持仓和回测

- `virtual_positions`
- `virtual_lots`
- `virtual_transactions`
- `virtual_cycles`
- 回测和虚拟交易记录必须归属于用户和策略版本

### 6.4 策略、学习和提前布局

- `strategy_assignments`：用户启用的策略及版本
- 策略学习快照、日复盘和实验结果按用户保存
- 提前布局雷达保存结果按用户保存
- 公共算法版本不按用户复制，个人启用状态和结果需要隔离

### 6.5 收件箱

- `signal_alerts`：消息内容、信号价格、建议数量、原因、状态和用户归属
- 消息已读、执行买入、执行卖出和取消状态写入云端
- 相同信号周期使用唯一键防止重复消息
- 交易执行使用 `alert_id` 或独立幂等键防止重复执行

### 6.6 审计

`audit_events` 至少记录：

- 用户 ID
- 事件类型
- 目标实体类型和 ID
- 操作时间
- 设备或客户端标识
- 成功或失败结果
- 非敏感摘要

不得记录密码、完整令牌或管理员密钥。

## 7. 数据加载与缓存

### 7.1 首次加载

登录成功后：

1. 获取当前账户资料。
2. 并行加载证券工作台必要数据。
3. 建立该用户的 Realtime订阅。
4. 数据加载完成后显示工作台。
5. 不得先显示上一用户的缓存再异步替换。

### 7.2 本地缓存

- 本地缓存必须以用户 ID 命名空间隔离。
- 退出登录时清空内存状态和当前用户缓存视图。
- 缓存仅用于加速读取和网络中断时只读展示。
- 云端是冲突处理和跨设备恢复的权威来源。

### 7.3 公共市场数据

- 实时行情、K线和股票目录不写入个人数据库。
- 用户自选股代码用于决定需要请求哪些公开行情。
- 行情刷新不会覆盖用户的股池、持仓或策略数据。

## 8. 多设备同步与冲突

### 8.1 Realtime

同一账户的其他设备变更以下数据时，当前页面自动更新：

- 自选股和分组
- 实际持仓和交易
- 虚拟持仓
- 策略配置
- 收件箱状态
- 提前布局保存结果

### 8.2 乐观并发控制

- 可编辑记录带 `version` 和 `updated_at`。
- 更新请求携带读取时的版本号。
- 版本不匹配时拒绝覆盖，并返回云端最新记录。
- 页面提示“数据已在其他设备更新”，加载最新结果。

### 8.3 交易幂等

- 买入、卖出、补仓和减仓操作必须带唯一幂等键。
- 同一信号在两个设备同时点击，只能成功执行一次。
- RPC必须在同一事务内检查幂等键并写入所有相关记录。

### 8.4 离线

- 网络中断时允许只读查看该账户最近缓存。
- 持仓交易、消息执行和数据迁移不得静默排队自动重放。
- 网络恢复后，由用户重新确认交易类操作。
- 普通非交易设置可在检测到版本一致后重试。

## 9. 首次登录和旧数据迁移

### 9.1 迁移入口

检测到当前浏览器存在旧版证券数据时，显示“一键导入现有证券数据”。

导入前显示：

- 自选股池数量和股票数量
- 实际持仓和交易数量
- 虚拟持仓和交易数量
- 策略和学习数据数量
- 收件箱消息数量
- 提前布局保存结果数量

用户必须勾选确认后才执行导入。

### 9.2 幂等导入

- 导入记录使用稳定 `source_id` 去重。
- 同一账户重复导入不会生成重复股池、持仓或交易。
- 部分失败时保留成功部分，并显示失败类别。
- 重试仅处理未成功的数据。

### 9.3 防止错误账户导入

- 登录后不自动导入。
- 用户可取消并退出当前账户。
- 成功导入后，本地数据标记为已迁移到该用户。
- 同一份本地数据不能默认导入另一个账户。
- 如确需复制到其他账户，必须走单独的“复制导入”确认流程。

### 9.4 回滚保护

- 迁移阶段保留本地只读备份。
- 云端导入完成并通过数量校验前，不删除本地原数据。
- 正式切换后以云端为准。

## 10. 生产环境与部署

### 10.1 Supabase

必须建立线上 Supabase 项目，并配置：

- Project URL
- anon public key
- 邮箱验证
- 密码重置回调 URL
- Netlify正式域名和本地开发域名
- 数据库迁移和 RLS 测试

### 10.2 Netlify

- Netlify部署前端生产包。
- 生产构建从 Netlify环境变量或受控的本地生产环境读取 `VITE_SUPABASE_URL`、`VITE_SUPABASE_ANON_KEY` 和必要的公开配置。
- 手动上传 `dist` 时，线上 Supabase公开配置必须在本地构建前提供。

### 10.3 构建保护

生产构建必须失败于以下情况：

- Supabase URL缺失
- anon key缺失
- Supabase URL为 localhost、127.0.0.1 或其他本机地址
- 前端环境中出现 service_role key

这可以防止再次上传只能在本机工作的登录版本。

## 11. 错误处理

- 云端写入失败时，不更新成“已保存”状态。
- 单个模块加载失败时显示模块级错误和重试入口。
- 身份验证失败使用可理解的中文提示。
- 会话失效时停止个人数据请求并返回登录页。
- Realtime断开时显示同步状态，并自动重连。
- 交易 RPC冲突或重复执行时显示明确结果，不重复修改本地持仓。
- 数据迁移显示逐类别进度和失败详情。

## 12. 安全和商业化基础

- 注册、登录和密码重置启用频率限制。
- 用户可导出自己的证券个人数据。
- 账户注销前二次确认。
- 删除账户支持可配置延迟删除期。
- 管理员不得通过前端 anon key绕过 RLS。
- 后续订阅、机构账户和团队权限可在本账户模型之上扩展，但不属于本阶段。

## 13. 实施顺序

### 批次 1：账户入口与生产环境

- 线上 Supabase项目和邮件认证
- 登录、注册、验证和密码重置
- 证券路由保护
- 登录后进入 `/securities`
- 生产环境构建保护

### 批次 2：核心个人数据

- 自选股和分组
- 实际持仓、T+1批次和交易
- 首次登录一键迁移
- Realtime同步和版本冲突处理

### 批次 3：策略与消息

- 虚拟持仓和回测记录
- 策略配置和策略学习
- 提前布局保存结果
- 收件箱、消息状态和交易幂等
- 审计轨迹

### 批次 4：验证与切换

- 完成跨账户、跨设备和迁移测试
- 关闭证券个人数据的旧本地写入路径
- 构建生产包
- 在 Netlify正式环境验收

## 14. 测试要求

### 14.1 账户隔离

- 两个不同账户同时登录。
- A账户创建的数据对B账户不可见。
- B账户无法通过修改请求参数读取或修改A账户数据。
- 退出A后页面不残留A的数据。

### 14.2 同账户多设备

- 两台设备登录同一账户。
- 一台新增自选股，另一台自动出现。
- 一台修改持仓组，另一台自动更新。
- 同一记录并发更新产生版本冲突而不是静默覆盖。

### 14.3 交易

- 同一信号在两个设备同时执行，只生成一条交易。
- 持仓、批次、交易记录和消息状态保持一致。
- T+1可用股数在跨设备读取时一致。
- 网络失败不会伪装交易成功。

### 14.4 迁移

- 未确认时不导入。
- 重复导入不重复数据。
- 错误账户不会自动接收旧数据。
- 部分失败可以继续重试。
- 导入前后数量校验一致。

### 14.5 部署

- 生产包不包含 localhost Supabase URL。
- 未登录访问证券页面跳转登录页。
- 邮箱注册、验证、登录、退出和密码重置在 Netlify正式域名可用。
- 刷新深层证券路由仍能正常加载。
- 换电脑登录后个人数据恢复。

## 15. 验收标准

- 新用户可自行注册并完成邮箱验证。
- 登录后直接进入空白的个人证券工作台。
- 不同用户同时使用时数据完全隔离。
- 同一用户多设备同时使用时数据实时同步。
- 当前用户可一键导入旧证券数据，且重复执行不产生重复。
- 刷新、关闭浏览器和更换电脑后个人数据仍存在。
- 退出后不显示上一位用户的数据。
- 交易、消息和持仓变更具备事务一致性和幂等保护。
- Netlify生产包使用线上 Supabase，不包含本机地址。
- 个股分析算法和基金模块不受本次改造影响。
